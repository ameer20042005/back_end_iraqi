## 1. لماذا هذه الخطة

التصميم الحالي مبني على قرار معماري واحد:

> **«حمّل كل شيء من باك اند السستم، احقنه بالبرومبت، وخلّ الموديل يبحث فيه.»**

كان قراراً **صحيحاً** بمقياس عشرات السجلات ومصدر بيانات محلي. مع خادم حقيقي وآلاف السجلات ينقلب لعطل، ومعظم أعراضه **صامتة** — لا استثناء، لا خطأ باللوق، فقط بوت يجيب إجابات خاطئة بثقة.

### المبدأ الحاكم للخطة كلها

> ## الموديل ليس محرك بحث.
> ## الموديل **مترجم** بين لغة الإنسان والاستعلام.

قاعدة البيانات تبحث بين مليون صف بميلي ثانية بالفهارس. الموديل يقرأ 40 صفاً بصعوبة ويهلوس. التصميم الحالي يكلّف الموديل بعمل قاعدة البيانات.

**الدورة المستهدفة:**

```
سؤال الموظف بالعراقي
      ↓
  الموديل  ──►  يفهم النية ويستخرج المعاملات فقط
      ↓          {status: "قيد التوصيل", city: "بغداد", limit: 10}
      ↓
باك اند السستم ──►  SQL مفهرَس على مليون صف، بميلي ثانية
      ↓
  10 نتائج + العدد الكلي   ← ~1,500 توكِن، لا 150,000
      ↓
  الموديل  ──►  يصوغها بالعراقي
```

---

## 2. الحساب الذي يفرض الخطة

الطلب الواحد يُحقن كسطر JSON كامل (`app/context_blocks.py::orders_context_block`) ≈ **150 توكِن** (العربي مكلف توكنياً، و`ensure_ascii=False` يبقيه خاماً).

```
10,000   إجمالي النافذة (settings.max_model_len)
-2,000   البرومبت النظامي + مرجع اللهجة
-1,500   تاريخ المحادثة (ينمو كل دور)
-  500   مساحة الرد
─────────
 6,000   المتاح للحقن  ÷ 150 = ~40 طلباً
```

| عدد الطلبات | التوكِنات المطلوبة | النافذة | النتيجة |
|---|---|---|---|
| 40 | 6,000 | 10,000 | ✅ يشتغل |
| 100 | 15,000 | 10,000 | ❌ |
| 1,000 | 150,000 | 10,000 | ❌ **15×** |
| 10,000 | 1,500,000 | 10,000 | ❌ **150×** |

**السقف الفعلي ~40 سجلاً.** لا مجال للتوسيع بالضبط: مضاعفة `max_model_len` تكسب 40 سجلاً وتخسر ضعف الذاكرة وسرعة الاستدلال.

**لم يظهر بعد** لأن بيانات الاختبار صغيرة. تحت الأربعين كل شيء صحيح فعلاً.

## 4. المرحلة 0 — مطابقة العقد (قبل أي كود)

> **⛔ لا تبدأ أي مرحلة أخرى قبل إتمام هذه.** بدونها كل ما بعدها تخمين غير مُتحقَّق.

### المخرج المطلوب: جدول من ثلاثة أعمدة

| المسار | العقد المكتوب | الواقع بالخادم | الفجوة |
|---|---|---|---|
| `GET /products/search` | | | |
| `GET /products/{id}` | | | |
| `GET /orders/{order_id}` | | | |
| `GET /orders/search` | | | |
| `GET /orders` | | | |

لكل مسار سجّل ثلاثة أشياء:

- [ ] **المسار والفعل** — موجود بهذا الاسم؟ *(خطأ = 404 على كل استعلام)*
- [ ] **أسماء الحقول** — `name` أم `product_name`؟ `in_stock` أم `available`؟ *(خطأ = حقول `None` صامتة — الأخطر)*
- [ ] **المصادقة** — `X-API-Key` أم `Authorization: Bearer`؟

### وأسئلة القدرات (تحدد المرحلة 3)

- [ ] هل يدعم `limit` / `offset`؟ **← الأهم على الإطلاق**
- [ ] هل يوجد `count` / `total` بالرد؟
- [ ] هل يبحث بالاسم والمدينة بجهته؟
- [ ] هل يوجد مسار حقيقي لـ«كل الكتالوج»، أم `search` بلا `q` هو الحل؟
- [ ] هل يطبّق فلاتر التاريخ فعلاً، أم يتجاهلها؟ *(يحسم إزالة الفلترة المحلية المزدوجة)*

### قرار لكل فجوة

| الحل | متى | الكلفة |
|---|---|---|
| **عدّل عندك** (طبقة المستودع) | الفرق تسموي فقط | رخيص — **الافتراضي** |
| **عدّل باك اند السستم** | مسار ناقص أو بيانات غير مُرجَعة أصلاً | تعديل المشروع الآخر |
| **طبقة تحويل** (adapter) | الخادم يخدم مستهلكين آخرين ولا يمكن تغييره | تعقيد دائم |

> **⚠️ مبدأ ثابت:** التحويل يعيش **حصراً** بطبقة المستودع (`HttpProductRepository` / `HttpOrderStatusProvider`). لو تسرّب اسم حقل خام لطبقة الأداة أو البرومبت، ضاعت قيمة العزل كلها.

## 8. قرارات معلّقة

| # | القرار | يحسمه | يؤثر على |
|---|---|---|---|
| 1 | هل باك اند السستم يدعم `limit`/`offset`؟ | المرحلة 0 | المرحلة 2 — تصفيح حقيقي أم خطة بديلة |
| 2 | هل يوجد `/orders/count`؟ | المرحلة 0 | المراحل 3 · 6 |
| 3 | هل يبحث بالاسم/المدينة بجهته؟ | المرحلة 0 | المرحلة 3 — أي معايير نعرضها للموديل |
| 4 | هل يوجد مسار «كل الكتالوج» حقيقي؟ | المرحلة 0 | المرحلة 8 · العطل A3 |
| 5 | هل يطبّق فلاتر التاريخ فعلاً؟ | المرحلة 0 | إزالة الفلترة المحلية المزدوجة |
| 6 | متى نشدّ سياسة التسامح بـ`system_backend_schema.py`؟ | بعد المرحلة 0 | العطل A1 — الحقول الجوهرية تصير إلزامية |

### بخصوص القرار 6 — تشديد التحقق

```
قبل  (خادم مجهول):   كل الحقول Optional  ·  extra="allow"  ·  استبعاد صامت
بعد  (خادم معلوم):   الحقول الجوهرية إلزامية  ·  الفشل يُسجَّل بوضوح
```

**«الجوهري»** = ما بدونه يصير الجواب خاطئاً لا ناقصاً:
- **منتج:** `id` · `name` · `price` — منتج بلا سعر لا يُعرض على زبون
- **طلب:** `order_id` · `status` — طلب بلا حالة عديم الفائدة بميزة تتبع

الباقي (`barcode`, `eta`, `current_stage`, `assigned_transporter`) يبقى اختيارياً بحق.
و`extra="allow"` **يبقى** — يحمي من الكسر عند إضافة حقول جديدة مستقبلاً.

## 9. ما لا تغيّره

هذه قرارات صحيحة بالتصميم الحالي — **لا تمسّها**:

| القرار | لماذا يبقى |
|---|---|
| **المسار الحتمي بالدعم** | أفضل جزء بالتصميم. الموديل **يخترع حالات طلب** (موثّق بالكود) — إخراج التتبع الدقيق من يده قرار صحيح، ويتوسّع بلا حدود |
| **الطبقة المجرّدة** (`ProductRepository` / `OrderStatusProvider`) | هي ما يجعل كل هذه الخطة ممكنة بلا لمس الراوترات والبرومبتات |
| **`guided_json`** بدل native tool calling | الآلية الأساسية متطابقة (كلاهما structured outputs بجهة vLLM)، والمكسب تجميلي — بينما موديلك مدموج/مضبوط وغير مختبَر على توكنات الأدوات |
| **`SystemProduct` / `SystemOrder`** كطبقة تحقق | شبكة الأمان الوحيدة ضد تغيّر شكل الخادم. تُشدَّد (القرار 6) لا تُحذف |
| **`is_pure_chitchat`** | يوفّر جولة توليد كاملة على التحيات |

## 10. ملاحظة على MCP

نوقشت فكرة تحويل الميزات لـ MCP لغرضين: تسهيل الدمج مع باك اند السستم، والوصول لقاعدة البيانات. **الخلاصة: MCP لا يخدم أياً منهما.**

- **للدمج:** اتجاه البروتوكول معكوس — أنت **المستهلك**، فالخادم هو من يبني MCP لا أنت. والدمج معطّل بسبب عدم تطابق العقد (المرحلة 0)، لا بسبب البروتوكول. طلب REST من الفريق الآخر أسهل بكثير من طلب MCP SDK + session manager + streamable HTTP.
- **لقاعدة البيانات:** الوصول المباشر يكسر ثلاث طبقات حماية قائمة (عزل المستأجرين بمفتاح API · التحقق بالعقد · صفر تخزين محلي). ولو كان المقصود «الموديل يبني SQL» فهي قناة حقن مباشرة: نص زبون حر → موديل مضبوط على لهجة → SQL → قاعدة إنتاج.
- **لو لزم وصول DB فعلاً:** أدوات استعلام **ثابتة ومعامَلة** (SQL مكتوب مسبقاً، parameterized) + مستخدم DB للقراءة فقط + عزل المستأجر يُنقل لعندك (`WHERE tenant_id = ?`). **بلا MCP** — حلقة الأدوات القائمة تكفي.

**الاستخدام المشروع الوحيد لـMCP:** تصدير أدواتك (`search_products`, `get_order_status`) لعملاء AI خارجيين. `voice_followup` غير صالح للتصدير (مخرجات صوت خام + حالة بالهيدرات + حلقة أدوار متعددة).

هذا الملف يعالج المشكلة الحقيقية. MCP قرار منفصل يُتخذ لاحقاً لو ظهر عميل خارجي فعلي.
