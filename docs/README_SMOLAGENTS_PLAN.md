# خطة دمج `smolagents` لتحسين الدقة والأداء

هذا المستند يشرح طريقة إدخال `smolagents` إلى `back_end_iraqi` بصورة تدريجية وآمنة. الهدف ليس استبدال منطق المشروع الحالي فوراً، بل رفع جودة اختيار الأدوات وتقليل الاستدلال غير الضروري مع إبقاء طبقات التحقق الحالية هي مصدر الأمان النهائي.

## النتيجة المستهدفة

- إجابات المبيعات لا تذكر سعرًا أو مخزونًا إلا من كتالوج حي.
- إجابات الدعم لا تخمّن حالة طلب؛ الحالة تأتي من نظام الطلبات فقط.
- التحيات والأسئلة ذات المعرفات الواضحة تمر بمسارات حتمية سريعة بدل دورة وكيل كاملة.
- الطلبات الغامضة أو متعددة النية تستخدم وكيلًا محدود الصلاحيات لاختيار الأداة المناسبة.
- يبقى إنشاء الطلبات واستخراج JSON تحت `guided_json` والحراس الحالية.

## ما هو موجود حاليًا

المشروع يعتمد FastAPI مع خادم vLLM متوافق مع OpenAI، ويحتوي بالفعل على عناصر يجب المحافظة عليها:

| العنصر | مكانه | السبب |
|---|---|---|
| حلقة استدعاء الأدوات المقيدة | `app/tool_loop.py` | تمنع تمرير مخرجات غير منظمة من النموذج. |
| حراس الأسعار وأسماء المنتجات | `app/guards.py` | تمنع الهلوسة بعد التوليد. |
| أدوات الكتالوج والطلبات | `app/tools/products.py`, `app/features/support/router.py` | هي المصدر الوحيد للبيانات الحية. |
| مسار التتبع الحتمي | `app/features/support/router.py` | رقم الطلب أو الهاتف لا يجب أن يعتمد على قرار النموذج. |
| vLLM وcontinuous batching | `app/engine.py` | أساس الأداء والتزامن؛ لا يُستبدل. |

## القرار المعماري

يُستخدم `ToolCallingAgent` وليس `CodeAgent`.

`ToolCallingAgent` يعمل باستدعاءات JSON منظمة، بينما `CodeAgent` يولّد ويشغّل Python. لأن هذا الباك-إند يتعامل مع كتالوج وطلبات وبيانات عملاء، لا يسمح التصميم بتشغيل كود مولد من النموذج أو بإتاحة أدوات عامة له.

```text
الطلب الوارد
    |
    +-- مسار حتمي سريع
    |     +-- تحية / شكر / هوية
    |     +-- رقم طلب واضح
    |     +-- رقم هاتف عراقي واضح
    |     `-- استخراج وإنشاء طلب JSON
    |
    `-- Smolagents ToolCallingAgent
          +-- search_products
          +-- get_order_status
          +-- count_orders
          `-- get_order_history
                    |
                    `-- guards + gateway + الرد النهائي
```

الموديل يقرر **أي أداة** يحتاجها فقط. لا يملك صلاحية الوصول الحر إلى HTTP أو قاعدة البيانات أو تنفيذ Python. مفاتيح API وهوية المستأجر لا تدخل ضمن معاملات النموذج؛ تبقى مربوطة من طرف الخادم كما هو معمول به حاليًا.

## مراحل التنفيذ

### 1. القياس قبل التغيير

أنشئ مجموعة تقييم عربية/عراقية مجهّلة من 300 إلى 500 حالة، موزعة بين:

- بحث منتج، سعر، توفر، مقارنة، وطلب ناقص أو مكتمل.
- تتبع بواسطة `ORD-...` أو الهاتف.
- أسئلة عامة، أسئلة متعددة النية، ولهجة عراقية مع أخطاء إملائية.
- أرقام عربية وهندية وإنجليزية.
- حالات مضادة: سعر مختلق، حالة طلب مختلقة، أو طلب أداة بمعاملات غير مسموحة.

لكل حالة يسجل النظام: الأداة المتوقعة، الأداة التي استدعيت فعليًا، عدد الخطوات، زمن النموذج، زمن الأداة، حجم السياق، ونتيجة الحراس.

### 2. توحيد عقود الأدوات

تكون الأدوات المتاحة للوكيل قليلة وصريحة:

```text
search_products(query, category?, in_stock_only?)
get_order_status(order_id?, phone?, status?, date_from?, date_to?, limit?, offset?)
count_orders(status?, date_from?, date_to?)
get_order_history(order_id)
```

المتطلبات لكل أداة:

- التحقق من المدخلات بـPydantic ورفض الحقول الزائدة.
- مخرجات JSON صغيرة وثابتة تشمل `found` أو `total` أو `has_more` عند الحاجة.
- مهلة مستقلة، كاش TTL، ورسالة خطأ قابلة للفهم.
- منع تحميل الكتالوج أو دفتر الطلبات كاملًا داخل prompt.

### 3. التشغيل في وضع Shadow

في هذه المرحلة يبقى `app/tool_loop.py` هو المسار الذي يجيب العميل. يعمل وكيل `smolagents` بالتوازي على عينة من الطلبات ويُسجّل قراره فقط، من دون تنفيذ أي عملية كتابة أو تغيير الجواب.

يقارن السجل بين:

- الأداة التي اختارها الوكيل والأداة التي استعملها المسار الحالي.
- المعاملات التي اقترحها الوكيل والعقد الصالح للأداة.
- عدد الخطوات وزمن الوكيل.
- حالات الفشل بسبب عدم توافق native tool-calling مع موديل vLLM الحالي.

هذا ضروري لأن الموديل الحالي يستعمل `guided_json` للأدوات، ولم يُثبت بعد أنه ينتج native tool calls المتوافقة مع `smolagents` بثبات.

### 4. التفعيل التدريجي

لا يُفعّل الوكيل كمسار منتج إلا بعد اجتياز معايير القبول. التسلسل المقترح:

1. 5% من أسئلة الدعم العامة فقط؛ يبقى رقم الطلب والهاتف حتميًا.
2. 20% من أسئلة المبيعات الخاصة بالبحث والمقارنة.
3. 50% مع مراقبة يومية للـP95 ونسب الهلوسة.
4. 100% للسيناريوهات التي اجتازت الاختبارات فقط.

يجب أن توجد قيمة إعداد مثل `AGENT_MODE=off|shadow|enabled` وfeature flag منفصل لكل من `support` و`sales` حتى يكون الرجوع إلى الحلقة الحالية فوريًا.

## حدود الأداء

| الإعداد | القيمة الابتدائية | الغرض |
|---|---:|---|
| `max_steps` | 2 | يمنع الدوران بين الأدوات في السؤال المعتاد. |
| الحد الأعلى للاستثناءات | 3 | فقط للسيناريو متعدد الخطوات بعد قياسه. |
| مهلة الوكيل | 8–12 ثانية | لا يسمح لوكيل جانبي بتعطيل طلب العميل. |
| `planning_interval` | معطل افتراضيًا | التخطيط يضيف استدعاءً وزمنًا؛ يُفعّل فقط عند وجود دليل قياسي. |
| الأدوات المتاحة | 4 للقراءة فقط | أصغر سطح صلاحيات ممكن. |

تستمر أدوات vLLM الحالية في استخدام `temperature=0.0`، لأن المشروع وثّق أن sampling غير مستقر للموديل المضبوط.

## معايير القبول

لا ينتقل النظام من `shadow` إلى `enabled` قبل تحقيق جميع الآتي على مجموعة تقييم ثابتة:

| المقياس | الحد المطلوب |
|---|---:|
| دقة اختيار الأداة | 95% أو أكثر |
| حالة أو سعر مختلق | 0% |
| مخرجات تخالف عقد الأداة | أقل من 0.5% |
| متوسط جولات الأدوات | 2 أو أقل |
| خفض توكنات السياق | 30% أو أكثر حيثما لا يلزم الحقن |
| P95 | تحسن 20% عن baseline أو لا يتراجع |
| فشل الوكيل | fallback آمن 100% من الحالات |

## الأمان وعدم التراجع

- لا يستخدم الوكيل `CodeAgent` ولا يملك `WebSearchTool` أو shell أو SQL حر.
- لا يُنشئ الوكيل طلبًا ولا يعدّل حالة طلب؛ عمليات الكتابة تبقى خلف بوابات التأكيد والحراس.
- أي تعطل في `smolagents` أو في توافق vLLM يعيد الطلب فورًا إلى `tool_loop.py`.
- لا تُحفظ نصوص العملاء الخام في telemetry؛ يحفظ فقط اسم الميزة، الأدوات، الزمن، وعدد الخطوات ونتيجة المقارنة.
- تبقى `guided_json` الطبقة المفضلة لاستخراج الطلبات من النص والصوت والصورة.

## التحقق والاختبارات

أضف الاختبارات التالية قبل التفعيل:

- اختيار `search_products` لأسئلة السعر والمنتج، وعدم اختياره للتحية.
- اختيار المسار الحتمي عند رقم طلب أو هاتف صحيح.
- رفض معاملات مثل `tenant_id` أو `api_key` أو حقول لم تُعرّف في العقد.
- إيقاف الوكيل بعد حد الخطوات وإرجاع fallback مفهوم.
- استمرار الحراس في حجب السعر أو اسم المنتج غير الموجود في نتيجة الأداة.
- اختبار حمل يقارن P50 وP95 واستهلاك التوكنات قبل وبعد التفعيل.
