# خطوات الرفع على RunPod

هذا الملف دليل تفصيلي خطوة بخطوة لرفع `back_end_iraqi` على RunPod عبر **Pod مباشر بصورة Ubuntu 22.04 خام** (الطريقة الوحيدة المعتمدة — لا حاجة لبناء أي صورة Docker مخصصة ولا حتى صورة vLLM جاهزة: `start.sh` يثبّت كل شي لازم من الصفر بأول إقلاع — Python/pip، vLLM 0.28.0 مع torch 2.13.0 (إصدارات مثبّتة في requirements-vllm.txt)، ffmpeg/libsndfile1 — انظر [start.sh](../../start.sh)). للتوثيق المرجعي لنقاط الـ API نفسها انظر [docs/api/](../api/overview.md)، وللوحة اختبار تفاعلية بالمتصفح انظر قسم [لوحة اختبار API](#لوحة-اختبار-api-test-console) بالأسفل.

---

## 🚀 التشغيل السريع — Pod جديد من الصفر

كل الخطوات بالترتيب، من إنشاء الـ Pod لحد أول رد من الوكيل. للتفاصيل والشروحات انزل لـ [خطوات النشر بالتفصيل](#خطوات-النشر-pod-مباشر-بالقالب-الجاهز).

### 1) أنشئ الـ Pod (من لوحة RunPod)

| الحقل | القيمة |
|---|---|
| **GPU** | A40 (48GB) أو أي GPU بـ 40GB+ |
| **Container Image** | `ubuntu:22.04` |
| **Container Disk** | 60GB+ |
| **Expose HTTP Ports** | `8000` |

اضغط **Deploy**، وانتظر حتى تصير الحالة **Running**.

### 2) افتح الطرفية

**Connect** → **Start Web Terminal**.

على صورة Ubuntu الخام، جهّز أدوات تنزيل المشروع وتشغيله بالخلفية أولاً (الطرفية بصلاحية root):

```bash
apt-get update
apt-get install -y git tmux curl ca-certificates
```

### 3) نزّل المشروع

```bash
cd /workspace
git clone https://github.com/ameer20042005/back_end_iraqi.git app
cd /workspace/app
```

### 4) شغّل السيرفر (يضل شغال بعد غلق الطرفية)

```bash
cd /workspace/app || exit 1
tmux kill-session -t api 2>/dev/null || true
tmux new-session -d -s api -c /workspace/app 'HF_HUB_ENABLE_HF_TRANSFER=0 bash start.sh > /tmp/api.log 2>&1'
```

### 5) راقب لحد ما يجهز

```bash
tail -f /tmp/api.log
```

أول تشغيل ياخذ **دقائق أطول من المعتاد** (صورة Ubuntu خام: تثبيت Python/pip + vLLM 0.28.0 + torch 2.13.0 أولاً، ثم تحميل الموديل ~24GB). اخرج من المراقبة بـ `Ctrl+C` — يوقف `tail` بس، ما يمس السيرفر.

### 6) تأكد إنه جاهز

```bash
curl --max-time 10 -i http://127.0.0.1:8000/health
curl --max-time 15 -i http://127.0.0.1:8000/health/llm
curl --max-time 10 -sS -o /dev/null -w 'HTTP %{http_code}\n' http://127.0.0.1:8000/test
```

نجاح `/health` و`/test` بحالة HTTP `200` يعني أن السيرفر والصفحة جاهزان. انتظر أيضاً حتى يرجع `/health/llm` حالة `200` و`"status":"healthy"` قبل اختبار التوليد. إذا تعذّر الاتصال بالمنفذ 8000، راجع `/tmp/api.log`؛ قد يكون السكربت ما زال يثبّت المتطلبات أو توقّف بسبب خطأ.

سجل الإقلاع يعرض مراحل مؤرخة تبدأ بـ `[boot ...]`؛ خطأ غير معالَج يعرض المرحلة ورقم السطر ورمز الخروج. عند ظهور `pip is looking at multiple versions` أو `Collecting ...` يكون التثبيت ما زال يحل التبعيات؛ هذا ليس وحده دليلاً على فشل. لا تعِد تشغيل الجلسة أثناء التثبيت. سجل `/tmp/vllm_boot.log` قد يخص التشغيل السابق حتى يصل السكربت إلى مرحلة إطلاق vLLM؛ قارن تاريخ تعديله عبر `stat`.

يبقى سكربت الإقلاع مشرفاً على FastAPI وvLLM بعد إطلاقهما. إذا انتهت إحدى العمليتين، يوقف الأخرى ويسجّل رمز الخروج؛ وإيقاف الجلسة يرسل إشارة الإنهاء للعمليتين اللتين أطلقهما السكربت.

### إعادة التشغيل والتخزين

يتحقق `start.sh` محلياً من إصدارات متطلبات Python وتبعياتها، بما فيها extras، قبل تشغيل pip. إذا كانت مكتملة يتجاوز التثبيت بالكامل؛ وإذا نقصت حزمة أو تغيّرت المتطلبات يثبّت المطلوب مع إعادة استخدام الحزم المطابقة، دون `--force-reinstall` أو ترقية إجبارية. تُفحص Chatterbox دون تبعياتها المتعارضة عمداً، ويُفحص torchaudio بعد ضبط مسارات CUDA. فشل استيراد vLLM يعرض الخطأ الفعلي ولا يعيد تنزيل الشجرة كاملة.

تُحفظ بيئة Python في `/workspace/app/.venv-pipecat` وكاش النماذج افتراضياً في `/workspace/.cache/huggingface`، وتشترك فيه نماذج الحوار والصوت. إذا وجد كاش Hugging Face القديم فقط، ينقله السكربت مرة واحدة ويحفظ رابطاً من المسار القديم، دون حذف ملفات الموديل. إذا كان المساران موجودين يستعمل القديم ويطبع ذلك في اللوج لتفادي تنزيل نسخة ثانية؛ يمكن اختيار المسار المطلوب صراحةً عبر `HF_HOME` أو `HF_HUB_CACHE`. التنزيل يعيد استخدام الملفات المكتملة ويجلب الملفات الناقصة؛ استئناف جزء من ملف منقطع يعتمد على مكتبة التنزيل. يجب الاحتفاظ بوحدة التخزين المركّبة على `/workspace` حتى تبقى الملفات بعد استبدال الحاوية.

ينظّف السكربت كاش تنزيلات pip القديم، ويثبّت الحزم باستخدام `--no-cache-dir`، دون حذف الحزم المثبّتة أو كاش النماذج. هذا يمنع تراكم كاش الحزم، لكن يلزم أن تتسع وحدة التخزين لبيئة Python وأوزان النماذج. خطأ `Disk quota exceeded` يحتاج مساحة أو حصة إضافية إن كانت الوحدة ممتلئة حتى بعد تنظيف كاش pip. لفحص المكان الفعلي:

```bash
df -h / /workspace
du -sh /workspace/app/.venv-pipecat /workspace/.cache/huggingface /root/.cache/huggingface 2>/dev/null
```

### 7) جرّب أول رد

```bash
curl -s -X POST http://127.0.0.1:8000/sales/chat \
  -H 'Content-Type: application/json' \
  -d '{"message":"شكد سعر لابتوب لينوفو؟"}' | python3 -m json.tool
```

لازم يرجع رد مبيعات عراقي بسعر من الكتالوج. لو رجع جملة اعتذار ثابتة مكررة، شوف [فحص صحة المُرمِّز](#فحص-صحة-المرمز-tokenizer).

### 8) افتح لوحة الاختبار بالمتصفح

```
https://<POD_ID>-8000.proxy.runpod.net/test
```

تلقى `<POD_ID>` بزر **Connect** → **HTTP Service [Port 8000]**.

### 9) اغلق الطرفية

السيرفر يضل شغال داخل tmux. للتأكد: افتح طرفية جديدة وشغّل `curl -s http://127.0.0.1:8000/health`.

## خطوات النشر: Pod مباشر بالقالب الجاهز

### الخطوة 1 — إنشاء الـ Pod

1. من لوحة RunPod، اضغط **Deploy** → **GPU Pod**.
2. قالب بصورة **`ubuntu:22.04`** خام (بدون Python ولا CUDA ولا PyTorch مسبقاً) — `start.sh` يبني كل شي لازم من الصفر بأول إقلاع: Python/pip، أدوات بناء، ffmpeg/libsndfile1، ثم vLLM 0.28.0 مع torch 2.13.0 (إصدارات مثبّتة في requirements-vllm.txt) (يلزم إصدار vLLM يدعم Qwen3.5). أي قالب ثاني فيه بعض هذي المكونات مسبقاً (صورة vLLM الرسمية، قالب PyTorch) يشتغل بنفس الموثوقية — كل خطوة تتخطى نفسها لو لقت الأداة موجودة أصلاً.
3. اختر GPU مناسب (انظر التوصية أعلاه).
4. تحت **Edit Template** (أو أثناء الإنشاء):
   - أضف `8000` إلى حقل **Expose HTTP Ports**.
   - تأكد أن حجم القرص (Disk / Container Disk) كافٍ (**60GB+** موصى به) — يشمل مساحة torch/vLLM المثبَّتة بأول إقلاع (~10-15GB) بالإضافة للموديل والمحوّل المُنزَّلين تلقائياً (~24GB).
5. اضغط **Deploy**.

### الخطوة 2 — نسخ المشروع للـ Pod

بعد ما يصير الـ Pod بحالة **Running**، افتح **Connect** → **Start Web Terminal** (أو اتصل بـ SSH لو فعّلته):

```bash
cd /workspace
git clone https://github.com/ameer20042005/back_end_iraqi.git app
cd /workspace/app
```

> ملاحظة: بقية هذا الدليل يفترض المسار `/workspace/app`. لو استنسخت باسم ثاني، بدّله بكل الأوامر أدناه.

### الخطوة 3 — إعداد القيم الثابتة

```bash
cd /workspace/app
nano app/config.py
```

لا يلزم توكن Hugging Face — كل الموديلات المستعملة عامة وتُنزَّل بلا مصادقة. وكل القيم (`model_name`، `vllm_port`، `max_model_len`، `gpu_memory_utilization`...) ثابتة في `Settings` داخل الملف نفسه؛ عدّلها هناك فقط عند الحاجة.

### الخطوة 4 — التشغيل (بـ tmux حتى يضل شغال بعد غلق الطرفية)

انسخ هذي الأوامر كما هي:

```bash
cd /workspace/app || exit 1
tmux kill-session -t api 2>/dev/null || true
tmux new-session -d -s api -c /workspace/app 'HF_HUB_ENABLE_HF_TRANSFER=0 bash start.sh > /tmp/api.log 2>&1'
```

هذا يبدأ سكربت الإقلاع بالخلفية ويخليه يستمر بعد غلق الطرفية. نجاح أمر `tmux new-session` يعني أن الجلسة بدأت؛ تحقّق من اللوج ونقاط الصحة حتى تتأكد أن التطبيق اشتغل فعلاً. الخيار `-c /workspace/app` يحدد مجلد المشروع، و`|| true` يسمح بالتشغيل حتى لو ما كانت جلسة `api` موجودة.

**ليش هيك مو `tmux new -s api` بعدين `bash start.sh`؟** لأن `new-session -d` تبدأ الجلسة **منفصلة أصلاً**، فما تحتاج تضغط `Ctrl+B` ثم `D` للخروج — وهذي الضغطة أكثر خطوة تنكسر بالعادة (لو انضغطت غلط تظهر كنص `^B^B` والسيرفر يموت مع الطرفية).

**ليش `HF_HUB_ENABLE_HF_TRANSFER=0` داخل أمر الجلسة؟** نمرّره مباشرة إلى `start.sh` حتى يستلمه أيضاً لو خادم tmux كان شغّالاً من قبل. بعض قوالب RunPod تضبطه على `1` بدون ما تكون حزمة `hf_transfer` مثبّتة، فيفشل التحميل بخطأ:
```
ValueError: Fast download using 'hf_transfer' is enabled ... but 'hf_transfer' package is not available
```
تصفيره يرجّع التحميل العادي. (بديل: `pip install hf_transfer`.)

#### متابعة الإقلاع

**أول تشغيل ياخذ وقت أطول** (تجهيز نظام التشغيل: Python/pip + vLLM 0.28.0 + torch 2.13.0 على Ubuntu الخام، ثم تحميل الموديل المدموج ~24GB من Hugging Face):

```bash
tail -f /tmp/api.log          # لوج FastAPI + خطوات start.sh
tail -f /tmp/vllm_boot.log    # لوج خادم vLLM نفسه (تحميل الأوزان)
```

اخرج من المتابعة بـ `Ctrl+C` — هذا يوقف `tail` فقط، ما يمس السيرفر داخل tmux.

السكربت يجهّز Python والمتطلبات أولاً، ثم يبدأ vLLM ويتأكد أن عمليته لم تتوقف مباشرة، وبعدها يشغّل FastAPI. لذلك `/health` و`/test` لا يستجيبان أثناء مرحلة التثبيت أو إذا فشلت. بعد بدء FastAPI قد تبقى خدمة النموذج غير جاهزة إلى أن يكتمل تحميل الأوزان؛ افحص `/health/llm` كما في [الخطوة 6](#6-تأكد-إنه-جاهز).

عند الحاجة إلى Python 3.12، ينشئ السكربت بيئة `.venv-pipecat` ويستخدمها دون تغيير Python النظام. وفي تثبيت vLLM يولّد ملف قيود مؤقتاً من `requirements.txt` و`requirements-gpu.txt`، ويحذف منه أسماء الإضافات مثل `[standard]` فقط، مع الحفاظ على الإصدارات. ويُمرّر ملفَي المتطلبات أيضاً إلى أمر تثبيت vLLM نفسه حتى يحترم المحلّل تبعيات Pipecat المشتركة (مثل `protobuf<7`)؛ ملف القيود وحده لا يضمّ شجرة تبعيات الحزم المذكورة فيه. تثبيت المتطلبات يبقي `uvicorn[standard]` وميزاته مفعّلة. لا تحتاج إنشاء ملف قيود يدوياً مع السكربت المحدّث.

#### أوامر tmux اللي تحتاجها

| الأمر | الفايدة |
|---|---|
| `tmux ls` | يعرض الجلسات الشغالة (لازم تشوف `api`) |
| `tmux attach -t api` | تدخل جلسة التشغيل؛ لعرض اللوج استخدم `tail -f /tmp/api.log` لأن الخرج محوّل إلى ملف |
| `Ctrl+B` ثم `D` | تطلع من الجلسة **بدون** ما توقف السيرفر (اضغطهن بالتتابع، مو سوية) |
| `tmux kill-session -t api` | توقف السيرفر نهائياً |

> ⚠️ لا تستخدم `Ctrl+C` أو `exit` وأنت داخل الجلسة — ينهون السيرفر.

#### تحقق إنه فعلاً نجا من غلق الطرفية

اغلق الطرفية، افتح وحدة جديدة، وشغّل:

```bash
tmux ls
curl -s http://127.0.0.1:8000/health
```

لو طلعت `api: 1 windows` ورد `{"status":"healthy"}` — تمام.

> **حدود tmux**: يحمي من غلق الطرفية فقط، **مو** من إيقاف الـ Pod أو إعادة تشغيله. لو أوقفت الـ Pod من لوحة RunPod تنفقد الجلسة ولازم تعيد أوامر الخطوة 4 يدوياً بعد إعادة التشغيل.

#### تحديث الكود لاحقاً

ارفع إصلاح `start.sh` إلى فرع `main` في GitHub أولاً؛ أوامر الـ Pod التالية تسحب النسخة المنشورة هناك. استعملها بعد حفظ أي تعديلات محلية تريد الاحتفاظ بها:

```bash
(
  set -e
  cd /workspace/app
  git fetch origin
  git checkout main
  git reset --hard origin/main
  tmux kill-session -t api 2>/dev/null || true
  tmux new-session -d -s api -c /workspace/app 'HF_HUB_ENABLE_HF_TRANSFER=0 bash start.sh > /tmp/api.log 2>&1'
)
```

> ⚠️ `git reset --hard` يمحي أي تعديل محلي بالـ Pod. لو عندك تعديلات تريد تحتفظ بيها، شغّل `git stash` قبله.

كتلة `set -e` توقف التحديث عند فشل Git، قبل إيقاف الجلسة وإعادة التشغيل. بعدها راقب `/tmp/api.log` وأعد فحوص `/health` و`/health/llm` و`/test` في الخطوة 6. مع النسخة المصحّحة من `start.sh` لا تحتاج أوامر `sed` المؤقتة؛ `git reset --hard` يستبدلها بنسخة المستودع.

#### تشخيص توقف الإقلاع

إذا اختفت جلسة `api` أو ظهر `Connection refused` أو كانت صفحة البروكسي غير متاحة، نفّذ داخل الـ Pod:

```bash
cd /workspace/app || exit 1
tmux ls
curl --max-time 5 -i http://127.0.0.1:8000/health
tail -n 100 /tmp/api.log
tail -n 100 /tmp/vllm_boot.log
```

ابدأ بخطأ `/tmp/api.log`. سجل vLLM قد يكون من تشغيل سابق إذا توقّف السكربت قبل بدء النموذج، وقد لا يوجد في أول تشغيل. إذا ظهر `ERROR: Constraints cannot have extras`، فالنسخة التي تعمل ما زالت تمرّر ملف المتطلبات مباشرة كقيود pip؛ حدّثها إلى `start.sh` الذي يحتوي الدالة `_install_vllm`. لا تحذف `[standard]` من المتطلبات ولا تغيّر إصدارات الحزم لمعالجة هذا الخطأ.

### الخطوة 5 — الوصول للسيرفر

الرابط العام يكون بالشكل:
```
https://<POD_ID>-8000.proxy.runpod.net
```

تلقى `<POD_ID>` بلوحة RunPod تحت تفاصيل الـ Pod، أو مباشرة بزر **Connect** → **HTTP Service [Port 8000]**.

تحقق من التشغيل:
```bash
curl https://<POD_ID>-8000.proxy.runpod.net/health
curl https://<POD_ID>-8000.proxy.runpod.net/gpu
```

`/gpu` يجب يرجع `"vllm_ready": true` بعد اكتمال تحميل الموديل.

## لوحة اختبار API (Test Console)

بعد ما يشتغل السيرفر (محلياً أو على RunPod)، افتح بالمتصفح:

```
http://localhost:8000/test          (محلياً)
https://<POD_ID>-8000.proxy.runpod.net/test   (على RunPod)
```

صفحة HTML/CSS/JS ثابتة (بدون أي تبعيات خارجية أو مكتبات) مبنية داخل المشروع (`static/index.html`)، تسمح باختبار كل نقاط الـ API من المتصفح مباشرة بدون Postman أو `curl`:

- **حقل رابط السيرفر** أعلى الشريط الجانبي — يستعمل آخر رابط محفوظ في المتصفح، أو رابط الصفحة الحالية إذا لم يوجد رابط محفوظ. على RunPod تأكد أنه `https://<POD_ID>-8000.proxy.runpod.net` إذا كانت الصفحة تفتح لكن لا تتصل بالسيرفر.
- **مؤشر حالة الاتصال** — يفحص `/health` و`/gpu` ويوضح إذا الموديل شغال فعلاً (`vLLM`) أو بوضع fallback بدون GPU.
- **خانات مفاتيح API** (مبيعات/دعم/إنشاء طلبات/متابعة صوتية) تحت مؤشر الحالة — معبّأة مسبقاً بنفس القيم الثابتة بـ`app/config.py`، وتُحفظ بمتصفحك (`localStorage`) فتقدر تعدّلها بعد تغيير المفاتيح بالملف. كل نقطة بالقائمة ترسل تلقائياً هيدر `X-API-Key` بالمفتاح المطابق لخدمتها.
- **كل نقطة براوترها الخاص** بالقائمة الجانبية:
  - `GET /health`, `/gpu`, `/` — زر إرسال واحد يعرض الـ JSON مع تلوين وترتيب تلقائي.
  - `POST /sales/chat` — واجهة محادثة كاملة (فقاعات رسائل)، تحافظ على `session_id` تلقائياً بين الرسائل، وتعرض تفاصيل الطلب (`order`) كبطاقة منسّقة لما يتثبّت.
  - `POST /sales/chat/stream` — نفس الفكرة لكن تعرض النص أولاً بأول أثناء البث (SSE)، مع قياس زمن أول توكن والزمن الإجمالي.
  - `POST /orders/create` — نموذج برفع ملف (صوت/صورة) أو حقل نص، حسب النوع المختار.
- **زر "عرض أمر curl المكافئ"** أسفل كل استجابة — يولّد أمر `curl` جاهز لنفس الطلب، مفيد للتوثيق أو الأتمتة لاحقاً.
- الصفحة تدعم **الوضع الداكن/الفاتح** (تلقائي حسب النظام، أو تبديل يدوي من الشريط الجانبي) وتُخزّن آخر رابط سيرفر ونقطة مفتوحة محلياً بالمتصفح (`localStorage`) لتوفير وقتك بالمرات القادمة.

> الصفحة تُقدَّم مباشرة من FastAPI نفسه (`GET /test` في [app/main.py](../../app/main.py)) فتفتح مباشرة بعد الرفع بدون أي إعداد إضافي أو استضافة منفصلة.

### فحص صحة المُرمِّز (tokenizer)

استخدم معرّف النموذج نفسه الموجود في `app/config.py`، دون نسخ مُرمّز من معمارية أخرى أو رفع أي ملفات:

```bash
python3 -c "
from transformers import AutoTokenizer
from app.config import settings
t = AutoTokenizer.from_pretrained(settings.model_name)
text = 'شكد سعر لابتوب؟'
print('model:', settings.model_name, 'vocabulary:', len(t))
print(t.decode(t.encode(text), skip_special_tokens=True))
assert len(t) > 100000
"
```

للتأكد من الصوت: افتح `/health/voice` وتحقق من `stt.model: ayoubkirouane/whisper-small-ar` ومن `stt.loaded` و`tts.loaded` بعد التحميل المسبق. `STT_DEVICE=cpu` يتيح نقل Whisper إلى CPU عند الحاجة، لكن زمنه يحتاج قياساً على جهازك. التفاصيل في [بنية الصوت](../pipecat-native-audio.md).
